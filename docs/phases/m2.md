## Execution and trust boundaries

The default runner executes argv without a shell inside a disposable non-root
container with no controller environment, App key, Docker socket or unrelated
host mounts. Snapshot input is streamed from exact Git objects into a temporary workspace; .git, credentials,
symlinks and path escapes are rejected. No repository-defined runner image or
privilege flags are accepted. Runner image/digest and resource limits are trusted
operator configuration. Default networking is disabled; optional external model/
HTTP evaluation requires an explicit separate evaluation access policy, not the
GitHub App's credentials. Docker isolation is a container boundary, not a claim
of VM-level isolation against kernel vulnerabilities.

The controller owns GitHub credentials and durable identity/evidence; the runner
receives only bounded evaluation data and separately scoped evaluation credentials
if the operator enables them. Credential-bearing control services never execute
reviewed scripts directly. CI eval execution and subsequent Check publication are
separate jobs/processes with separate permissions. Test-only local native command
execution must be explicit and restricted to trusted fixtures; it cannot certify
untrusted PR isolation.

## Contracts and comparison

EvalSuite v1alpha1 defines suite ID, explicit scenario IDs/requirement mapping,
class, impact categories/paths, adapter/argv, deadlines, trial thresholds and
optional model variants. Unknown keys and ambiguous suites fail validation. The
baseline's suite definition governs a comparison so a PR cannot erase a failing
scenario by deleting its manifest; additions/removals/config changes are reported.
Native structured JSON and existing engine JSON/JUnit reports normalize to a
versioned EvalRun contract. Logs are bounded data and never instructions.

A process exit zero alone is not behavioral success. Empty output, missing
scenarios, invalid reports, crashed evaluators, skipped assertions and insufficient
trials remain explicit. Metrics include observed latency/cost/token values when
provided; absent metrics are not fabricated. Statistical intervals describe the
sample under the configured model and do not certify universal safety.

## Implementation checkpoint

Phase-isolated release tracking and strict EvalSuite/EvalRun contracts are tested.
Project validation checks declared suites and requirement mappings; impact selection
uses the existing semantic review categories and reports uncovered requirements.
Trial aggregation distinguishes observed pass-rate thresholds from descriptive
Wilson confidence intervals: a configured sample can pass while its confidence
lower bound remains below the target. Missing/skipped trials are insufficient;
evaluator errors are infrastructure errors. Safety assertions default to critical
and tolerate zero critical failures. Metrics stay absent when observations are missing.
Execution/adapters/durable orchestration/live PR release acceptance remain open.


### Isolated runner checkpoint

The UBI runner pins Node 26.10.0, Python 3.14.8 and pytest 9.1.1. Python source
and every installed wheel have recorded checksums. Operators supply an immutable
runner image digest; manifests cannot select an image or grant privileges. The
runner receives snapshot files through stdin, with no host mounts or network.
It runs as UID 1001 with a read-only root filesystem, bounded temporary filesystems,
memory/CPU/process limits and a whitelisted child environment. Cancellation forces
container removal; a cleanup failure stops execution and requires operator action.

Pytest commands receive a managed JUnit path and xunit2 format. An optional scenario
`selector` maps a stable AgentCI ID to the JUnit `classname.name`; selectors must be
unique. Every declared scenario must appear exactly once, with no undeclared tests.
Exit 5 (no tests), collection/internal/usage errors, missing or invalid reports,
contradictory exit codes and output limits are infrastructure errors. Skipped tests
remain skipped and therefore cannot satisfy a complete passing trial sample.
Native reports use `{schemaVersion: "v1alpha1", results: [{scenario, status}]}`,
with optional observed latency/cost/token metrics and critical-failure markers.

Real Docker tests cover both native outcomes, pytest pass/fail/skip/no-tests and
collection errors, unavailable commands, secret/socket isolation, network denial,
read-only root, deadlines, cancellation, output limits, escaping/oversized reports
and cleanup. Full CI builds and scans this runner and requires the real tests.
The runner remains a local/CI implementation checkpoint, not a published M2 build.


### Repeated execution checkpoint

The execution primitive runs configured trials sequentially under an operator
trial budget (100 by default, explicitly configurable up to 1,000). Model-matrix
suites require an explicit configured variant. Both subjects run the baseline
suite definition; results bind repository, exact commit, suite revision, trial
count and model. Comparison rejects identity/configuration mismatches and missing
scenario coverage. It reports pass-rate and critical-failure deltas; infrastructure
errors and insufficient samples remain visible without being called behavioral
regressions. A cancelled run stops scheduling remaining trials.

Three real isolated baseline passes followed by three head assertion failures
produce the expected regression and statistical counts. This verifies the local
primitive. Persisted model-matrix orchestration, changed-suite coverage reports,
API/PR publication and released customer acceptance remain open.
