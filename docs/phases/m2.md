## Execution and trust boundaries

The default runner executes argv without a shell inside a disposable non-root
container with no controller environment, App key, Docker socket or unrelated
host mounts. Snapshot input is streamed from exact Git objects into a temporary workspace; .git, credentials,
symlinks and path escapes are rejected. No repository-defined runner image or
privilege flags are accepted. Runner image/digest and resource limits are trusted
operator configuration. Default networking is disabled; optional external model/
HTTP evaluation requires an explicit separate evaluation access policy, not the
GitHub App's credentials. Docker isolation is a container boundary, not a claim
of VM-level isolation against kernel vulnerabilities.

The controller owns GitHub credentials and durable identity/evidence; the runner
receives only bounded evaluation data and separately scoped evaluation credentials
if the operator enables them. Credential-bearing control services never execute
reviewed scripts directly. CI eval execution and subsequent Check publication are
separate jobs/processes with separate permissions. Test-only local native command
execution must be explicit and restricted to trusted fixtures; it cannot certify
untrusted PR isolation.

## Contracts and comparison

EvalSuite v1alpha1 defines suite ID, explicit scenario IDs/requirement mapping,
class, impact categories/paths, adapter/argv, deadlines, trial thresholds and
optional model variants. Unknown keys and ambiguous suites fail validation. The
baseline's suite definition governs a comparison so a PR cannot erase a failing
scenario by deleting its manifest; additions/removals/config changes are reported.
Native structured JSON and existing engine JSON/JUnit reports normalize to a
versioned EvalRun contract. Logs are bounded data and never instructions.

A process exit zero alone is not behavioral success. Empty output, missing
scenarios, invalid reports, crashed evaluators, skipped assertions and insufficient
trials remain explicit. Metrics include observed latency/cost/token values when
provided; absent metrics are not fabricated. Statistical intervals describe the
sample under the configured model and do not certify universal safety.

## Implementation checkpoint

Phase-isolated release tracking and strict EvalSuite/EvalRun contracts are tested.
Project validation checks declared suites and requirement mappings; impact selection
uses the existing semantic review categories and reports uncovered requirements.
Trial aggregation distinguishes observed pass-rate thresholds from descriptive
Wilson confidence intervals: a configured sample can pass while its confidence
lower bound remains below the target. Missing/skipped trials are insufficient;
evaluator errors are infrastructure errors. Safety assertions default to critical
and tolerate zero critical failures. Metrics stay absent when observations are missing.
Execution/adapters/durable orchestration/live PR release acceptance remain open.


### Isolated runner checkpoint

The UBI runner pins Node 26.10.0, Python 3.14.8 and pytest 9.1.1. Python source
and every installed wheel have recorded checksums. Operators supply an immutable
runner image digest; manifests cannot select an image or grant privileges. The
runner receives snapshot files through stdin, with no host mounts or network.
It runs as UID 1001 with a read-only root filesystem, bounded temporary filesystems,
memory/CPU/process limits and a whitelisted child environment. Cancellation forces
container removal; a cleanup failure stops execution and requires operator action.

Pytest commands receive a managed JUnit path and xunit2 format. An optional scenario
`selector` maps a stable AgentCI ID to the JUnit `classname.name`; selectors must be
unique. Every declared scenario must appear exactly once, with no undeclared tests.
Exit 5 (no tests), collection/internal/usage errors, missing or invalid reports,
contradictory exit codes and output limits are infrastructure errors. Skipped tests
remain skipped and therefore cannot satisfy a complete passing trial sample.
Native reports use `{schemaVersion: "v1alpha1", results: [{scenario, status}]}`,
with optional observed latency/cost/token metrics and critical-failure markers.

Real Docker tests cover both native outcomes, pytest pass/fail/skip/no-tests and
collection errors, unavailable commands, secret/socket isolation, network denial,
read-only root, deadlines, cancellation, output limits, escaping/oversized reports
and cleanup. Full CI builds and scans this runner and requires the real tests.
The runner remains a local/CI implementation checkpoint, not a published M2 build.


### Repeated execution checkpoint

The execution primitive runs configured trials sequentially under an operator
trial budget (100 by default, explicitly configurable up to 1,000). Model-matrix
suites require an explicit configured variant. Both subjects run the baseline
suite definition; results bind repository, exact commit, suite revision, trial
count and model. Comparison rejects identity/configuration mismatches and missing
scenario coverage. It reports pass-rate and critical-failure deltas; infrastructure
errors and insufficient samples remain visible without being called behavioral
regressions. A cancelled run stops scheduling remaining trials.

Three real isolated baseline passes followed by three head assertion failures
produce the expected regression and statistical counts. This verifies the local
primitive. Persisted model-matrix orchestration, changed-suite coverage reports,
API/PR publication and released customer acceptance remain open.


### Model selection and image scan checkpoint

Model-impact selection now reports an explicit gap if no required representative
suite exists or its model matrix is absent. Matrix execution covers every
configured variant on both commits, under a separate total-trial budget. Planning
loads manifests as data from both snapshots, preserves baseline definitions,
reports added/removed/modified suites and scenarios, and exposes unmapped or
unknown requirements even when a malformed mapping would otherwise go unselected.

The first full runner CI attempt passed execution and packaging but failed the
image scan on build-only package managers' vendored dependencies. That failure
is retained. The runtime removes npm, pip and ensurepip after installing pinned
runtime dependencies. Real Python/pytest/Node execution remains available; custom
engine dependencies must be provisioned in an operator-reviewed immutable image,
not installed by a PR in the default offline runtime. The hardened local image
scans with zero findings; full CI and release/platform scans remain required.


### Baseline assertion provenance checkpoint

Comparison freezes the baseline evaluation namespace (`spec.evals.include`) and
optional explicit `runner.harness` paths. Head edits/deletions of those assertion
files cannot suppress baseline regressions; subject implementation files remain
from the requested head. Assertion dependencies outside that namespace must be
listed explicitly, including shared helpers or test configuration when applicable.
Bundle revision covers the manifest and baseline input digests. EvalRun requires
subject/assertion commit IDs, exact runner image, runtime input digest and omitted
protected paths. The input projection excludes tracked credential/template paths
such as `.env.example`, and reports those omissions rather than silently claiming
the full tracked tree was executed. Explicit protected harness inputs fail.

Real container tests verify a head replacing its eval script with `process.exit(0)`
or deleting it still fails against the fixed baseline assertion and changed subject.
The existing released M1 API is unchanged; these are unreleased M2 domain contracts.
Exact-source full CI for this provenance extension passed 91 unit/API/domain
tests and four real integration tests with zero skips. The artifact digest and
matching candidate/CI trees are recorded in `releases/m2-provenance-ci.json`.
The primitive's task acceptance is closed; final M2 release verification remains.

### Optional engine checkpoint

The separate `eval-engines` UBI image installs Promptfoo 0.123.1 and DeepEval
4.2.8. The default runner stays small; operators select an immutable image
appropriate for their declared adapters. Promptfoo has a committed npm lockfile;
DeepEval and its Python dependencies have exact versions and official wheel
hashes, with source builds disabled. Both engines use the existing offline,
non-root, disposable runner boundary. Telemetry and dotenv loading are disabled;
provider credentials are not inherited from the controller.

Promptfoo writes a managed JSONL report, with one repeat and no cache or database
write. A scenario selector is `testIdx:promptIdx` (for example `0:0`). Every
declared scenario must appear exactly once. Its exit 100 is an assertion failure
only when the structured grade confirms that outcome; missing grades or an
execution failure remain errors. The engine's `error` field can also contain an
ordinary failed assertion explanation. Raw outputs, provider errors and assertion
text are excluded from the normalized scenario record.

DeepEval runs through its actual pytest plugin and the managed JUnit adapter.
Tests use the upstream built-in `ExactMatchMetric`, with no external model or
API key, to verify both pass and fail behavior. Collection failures remain errors.
Actual engine tests cover these outcomes and container removal. CI builds the
optional image and supplies its immutable ID so these tests cannot silently skip.

The local arm64 image scan retains one high-severity `node-forge` finding with no
published fix. It is not a clean scan or a release exception. The full release
assessment must cover the selected image's provider capabilities and all native
platforms. HTTP release acceptance, external provider deployment configuration,
durable orchestration, PR/API acceptance, publication and release gates remain open.

### HTTP adapter checkpoint

HTTP evals now use the default repeated-trial, frozen-assertion and model-matrix
pipeline. Strict request/response schemas bind UUID, exact source, effective input
digest, suite revision, provider revision and model. Repository manifests select
only a provider ID; operator configuration controls the HTTPS endpoint, literal
IP, verified trust root and separately scoped authorization. No DNS lookup or
redirect is allowed. Tests include encrypted success, untrusted/incorrect-host
certificates, every identity mismatch, private errors, request/response limits,
deadlines, cancellation and malformed results. HTTP evidence uses provider
identity/revision rather than claiming a local runner image executed the trial.
See [the provider contract](../http-eval-provider.md). Full CI acceptance remains
pending; this does not close durable orchestration or any release gate.

### Durable execution recovery checkpoint

The controller stages immutable projected base/head inputs and unit definitions in
PostgreSQL. Each unit has an exclusive expiring lease and normalized immutable
trial checkpoints. A replacement executor reuses committed observations; completion
recomputes statistics and provenance from retained trials rather than trusting an
executor's summary. Raw credential paths are omitted and recorded as provenance.
Completed runs reference the digest of their retained normalized trial record.

Containers carry exact unit and lease UUID labels. Recovery holds the database
unit lock while removing containers owned by prior leases, preserving other units
and the current lease. Maintenance renews ownership and repeats cleanup to cover
late daemon creation by an old process. Actual SIGKILL tests leave a live container,
expire its lease and recover through a new executor. Cancellation waits for runner
cleanup and prevents successful completion. Database failure or lease loss aborts
execution; stale owners cannot publish observations or results.

Execution is at least once before a trial checkpoint commits. Killing a worker
between an external action and its checkpoint can repeat that action. Committed
observations are not repeated; HTTP provider idempotency and stable request IDs
still need integration. These local tests do not certify Temporal replay, worker
credential isolation, published images or phase release acceptance. See
[local recovery evidence](../../releases/m2-durable-local.json).
