## API and domain decisions

| Surface | Required contract |
| --- | --- |
| Provider interface | `invoke`, `stream`, `capabilities`, optional `estimateCost`; provider identity is a trusted registration, not inferred from URL compatibility |
| Request | Stable request/attempt ID; messages/input; separate system/developer instructions; JSON-schema tool definitions and response schema; bounded model parameters; metadata; absolute deadline/retry policy; namespaced provider extensions |
| Response | Requested and observed provider/model, terminal status, bounded text/tool-call proposals, validated structured output, usage or explicit unknown values, sanitized request IDs/errors, latency and cost-estimate provenance |
| Stream | Ordered start/delta/tool-delta/usage/terminal events; partial JSON is never a completed finding; refusal, truncation, timeout, cancellation and errors stay explicit; unknown provider events cannot fabricate completion |
| Review | Organization/repository/PR/base/head, attempt, declared coding provider and provenance, reviewer provider/model/config/prompt/context digests, role, policy version and budget reservation |
| Finding | Stable ID and dedupe key, claim/category/severity, source model and exact file/evidence references; state transitions from proposed through reproduction to confirmed/unconfirmed/false-positive/resolved |
| Reproduction | Trusted bounded execution plan, immutable subject/assertion inputs, disposable M2 isolation, no App/provider credentials, owned cleanup, retained positive/negative execution evidence |
| Agent/API | Additive versioned requests/reads/export; request permission distinct from evidence-read permission; idempotency, exact subject binding, bounded pagination/export and shared fixtures; preserve M1/M2 compatibility |
| Dashboard | Read-only scoped review/eval/finding/evidence views; server-only credentials, secure server sessions, authorization on every data route, private caching and tested cross-tenant/expired/CSRF cases |

The compatibility gate checks both immutable released contracts: M1 `0.2.1-m1`
and M2 `0.3.1-m2`. The M2 baseline was extracted from the already downloaded
public package and matched byte-for-byte to frozen source `9bcff7d`. Identity
records in `specs/api/baselines/` bind each contract to its release and package.
`npm run check:api:compat` rejects removal of an M1 endpoint
and an M2-only endpoint; the latter remains compatible with M1 alone, proving why
both boundaries are required. Future breaking changes require an explicit version
and migration decision, not replacement of these baseline files.

Provider errors use stable categories such as invalid request, unsupported
capability, authentication, rate limit, deadline, cancellation, budget exhaustion,
transport failure, refusal and invalid output. SDK automatic retries must not
multiply controller retries. Streaming interruptions cannot be retried as if no
billable request occurred: record uncertain usage, reserve bounded retry budget
and preserve attempt identity. Missing usage is unknown, not zero cost.

`differentProvider: true` requires a known coding-provider identity and a distinct
trusted review-provider registration. Unknown provenance cannot satisfy the
rule. Provider aliases using the same upstream do not establish independence.
Provider/model selection and any fallback are recorded as evidence. Seven role
templates cover spec compliance, correctness, architecture, security, adversarial
review, test/eval completeness and operational reliability.

Repository text and model output are untrusted review data. Reviewers cannot
change policy, supply provider credentials or execute arbitrary reproduction
commands in the controller. Multiple matching model claims may increase priority;
confirmation requires evidence. An explicit customer blocking policy may act on
unconfirmed claims, but must retain that state and explain its policy basis.

Use standards-based OIDC with server-managed sessions for the dashboard; Keycloak
is the proposed local reference deployment under the Red Hat preference. The
library/version and operational issuer are finalized and verified in the session
PR. No browser-side operator bearer tokens, App keys or provider keys. Zod handles
UI input; backend validation and authorization are not delegated to client code.

Budget policy is fail-closed: missing authorization, unknown price bound or an
unreservable worst-case request prevents live dispatch. Reserve conservative
input/output cost before each attempt, including retries; settle known usage and
retain reservations for ambiguous charges until reconciled. The live acceptance
budget is separate from customer runtime policy. A local estimate is not proof of
provider billing; retain pricing/version provenance and compare reported usage.

## Official API grounding

OpenAI Responses streams have typed semantic events. The adapter must distinguish
terminal completion, errors and incomplete/refused output rather than parse every
text delta as a complete response. See [streaming](https://developers.openai.com/api/docs/guides/streaming-responses)
and [structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

Anthropic Messages streaming has message/content-block boundaries and cumulative
usage updates; an error can occur within a successful HTTP stream. Preserve
those distinctions in the shared event contract. See [streaming](https://platform.claude.com/docs/en/build-with-claude/streaming)
and [structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs).

xAI documents streaming and schema-directed output. Its adapter gets the same
conformance and live acceptance requirements; similar endpoint shapes are not
proof of equivalent semantics. See [streaming](https://docs.x.ai/developers/model-capabilities/text/streaming)
and [structured outputs](https://docs.x.ai/developers/model-capabilities/text/structured-outputs).
